# Kiro usage: what Kiro has and has not done, and the plan to do it for real

The rules say "Entrants must build a working software application using Kiro" and "Insufficient use of Kiro will result in disqualification". One fifth of the score asks "How thoroughly and skillfully does the project use Kiro?". This file keeps that honest. Part A records what exists. Part B is the work to do inside Kiro. Part C is how to capture evidence. Part D is the write-up template for the Devpost form.

## Part A: what exists today (6 Nov 2026), and how it was made

**Produced by Kiro: nothing.** Kiro has not been installed against this repository. It has not generated, loaded, checked or run any file here.

|---|---|---|---|
| `.kiro/steering/` (5 files, one `fileMatch`) | Written | By hand with an AI coding assistant outside Kiro, before the code | None. Not loaded by Kiro |
| `.kiro/specs/` (7 specs: EARS requirements, design, tasks) | 6 implemented, `contradiction-seance` not started | Same. Some were revised alongside the code. The `[x]` marks were set by hand | None. No task was run by Kiro. No Analyze Requirements |
| `.kiro/hooks/` (6 hooks, v1 JSON) | Written | Same. Compared with Kiro's published schema by `tests/kiro/kiro-config.test.ts` | None. **No hook has ever fired.** That test does not show Kiro accepts them |
| Source, tests, docs (4 to 6 Nov 2026) | Built; counts in TEST_REPORT.md | Same | None |
| `vendor/walnut/` | Pre-existing, unchanged | Earlier work by the Walnut team | None |
| `.kiro/agents/`, MCP config, Powers, `.kiro/skills/` | Do not exist | | None |

Spec files follow the documented folder layout, but nobody should read that as Kiro having written them. Each `tasks.md` carries the same statement.

An audit on 6 Nov 2026 found `leak-guard.json` using the legacy trigger name `PostTaskExecution`. It was changed to `PostTaskExec`, the name in the IDE 1.0 hook table. That shows why a schema check is not the same as a run: only Kiro can confirm it.

Everything in Part B produces real Kiro activity on top of this base. Even after Part B, the first version of the application will still have been built outside Kiro, and the write-up must say so. Judges decide what counts as sufficient. The more real work happens in Kiro from here on, the smaller that risk.

### B0. Set up (30 minutes)

1. Install Kiro IDE (and Kiro CLI if you want to compare surfaces). Sign in. In the CLI run `kiro-cli doctor`.
2. Request the free Kiroween credits before **1 Dec 2026 12:00 PT (2 Dec 04:00 SGT)**. Allow 48 business hours. Redeem them by 4 Dec.
3. Create the public GitHub repo, push this folder, open it in Kiro.

### B1. Steering (30 minutes)

1. Open the Steering panel. Confirm all five files load and that `10-governance-invariants.md` shows `fileMatch` inclusion.
2. Click Refine on `00-standards.md` and keep any wording you agree with.
3. Click Generate Steering Docs. Commit Kiro's `product.md`, `tech.md`, `structure.md` unedited (`kiro: generated steering`). Then restore anything Kiro got wrong in a second commit. Note one concrete difference for the write-up.
4. Evidence: screenshot of the Steering panel.

### B2. Hooks (30 minutes)

1. Open the Agent Hooks panel. All six hooks should appear without an upgrade badge. If any shows one, use "Ask Kiro to create a hook" to recreate it from its description and commit the result.
2. Fire `run-engine-tests`: ask Kiro in chat "Add a one-line doc comment to `findGhosts` in src/engine/ghosts.ts". File hooks only fire on agent edits, not your own saves.
3. Fire `dash-check`: ask Kiro to add a sentence with an em dash to a Markdown file and watch the hook make it fix the file.
4. Fire `spec-drift-review`: ask Kiro to add an acceptance criterion to `ghost-versions/requirements.md`.
5. Evidence: screenshot of each hook's output in the Kiro panel.

### B4. Build the Contradiction Seance with Kiro (2 to 4 hours, uses credits)

This is the main genuine Kiro build. Kiro writes the spec from the description below, then implements it.

1. Use Supervised mode.
2. Create the spec with Kiro first: start a new Feature Spec (Requirements-First) named `contradiction-seance-kiro` and paste the description at the end of this step. Commit Kiro's files unedited. Delete the hand-written `contradiction-seance` folder once Kiro's version is reviewed. Keep the `-kiro` suffix: `tests/kiro/kiro-config.test.ts` uses it to tell Kiro's specs from the hand-written ones. Run task 1 alone. Read the diff. If it is wrong, fix the spec, not the code.
3. Run all Tasks. The `leak-guard` hook (`PostTaskExec`) should run the leak tests after every task (this is its first real test: if it does not fire, recreate it in the Agent Hooks panel), and `run-engine-tests` rebuilds and smoke-tests the API after engine edits.
4. In the IDE, open design.md and look at the Correctness properties Kiro extracts. Make the property for requirement 3.2 (uniform output) a required property-based test task.
5. Verify yourself: `npm test`, `npm run build`, `npm run smoke:api`. Paste the real output into TEST_REPORT.md under a new dated heading.
6. Check `/usage` and note the credit cost.
7. Evidence: screenshots of the task list running, the diff of task 1, `/usage`. Commit `kiro: seance tasks 1 to 7`.

The description for step 2. Compare Kiro's requirements with the hand-written draft and note the differences for the write-up.

```text
GOAL
Add a contradiction seance to Stitchwork so a data steward can see living sources that disagree on a number, because ghost detection only catches old versions of the same document and misses echoes such as a chat message still saying "30 days" after the handbook moved to 14.

ACTORS
Any persona can open the Seance tab and sees only contradictions between passages they can open. Personas in the `steward` group see the same list; no persona sees a contradiction where either side is a passage they cannot open.

BEHAVIOUR
1. The user opens the Seance tab.
2. The system takes the passages that passed both permission gates for that persona and are not ghosts.
3. The system finds quantity mentions (a number followed by days, hours, percent, %, SGD or USD) and pairs mentions from different documents with the same unit, different values, and at least 2 shared context terms within 6 tokens of the number.
4. The system lists each contradiction with both quoted sentences, both sources and dates, and labels the side from the newer wiki page "likely current".
5. In the Laboratory, a cited passage that is part of a contradiction shows a "Disputed" badge.

INPUTS AND OUTPUTS
Input is the existing living passage set (under 1,000 passages). Output is at most 20 contradictions ordered by shared term count, highest first. Empty state text: "The spirits are quiet. No living sources disagree."

RULES AND EDGE CASES
Units normalise singular and plural (day and days). Two mentions in the same document are never paired. Numbers with thousands separators (20,000) parse as one number. If more than 20 pairs exist, show 20 and the text "Showing 20 of N". Archived documents never appear.

CONSTRAINTS
The seance output for a persona must be identical whether or not documents that persona cannot open exist (same property as P1 in permission-gates/design.md). No new runtime dependency. Computation for the bundled dataset finishes in under 200 ms in the browser.

EXISTING SYSTEM
Reuse the gate and ghost steps in #src/engine/engine.ts, the tokenizer in #src/engine/tokenize.ts, and the uniform-response harness in #tests/engine/uniform.property.test.ts. The draft spec already exists in #.kiro/specs/contradiction-seance/requirements.md. Do not change the ask pipeline order or any existing test.

OUT OF SCOPE
Automatic correction of the echo source, contradictions between non-numeric statements, any language model call, writing seance results to the Crypt.

DONE MEANS
New tests in tests/engine/contradictions.test.ts cover every acceptance criterion including a property-based test for the uniform-output constraint; `npm test`, `npm run build` and `npm run smoke:api` pass; the bundled dataset yields at least one contradiction (the 30 day echo in the claims-floor chat channel versus the 14 day handbook v2).
```

### B5. A Bugfix Spec on a real defect (45 minutes)

Known real defect to fix through a Bugfix Spec, so the write-up can compare Bugfix Specs with Feature Specs:

- REPRODUCTION: in Body parts, upload `notes.md` containing "alpha", then upload a different `notes.md` containing "beta".
- CURRENT: the first upload is silently replaced, because both get the document id `upload:notes-md:notes` (`src/engine/adapters/detect.ts`) and `Engine.addDocuments` replaces documents with an existing id. Confirmed on 4 Nov 2026 with a throwaway test: after two uploads only the "beta" passage remains.
- EXPECTED: the second upload is kept as a new document (for example `upload:notes-md-2:notes`) or replaces the first with a visible "replaced" message; choose one in the spec.
- UNCHANGED: uploads with distinct names behave as now; uploaded documents stay visible to `everyone`; existing adapter tests pass.
